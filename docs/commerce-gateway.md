# 自建计费网关协议 v1

协议标识：`yingban-commerce-gateway-v1`。**这是本项目定义的服务端集成协议，不是已发现或已获准使用的 Vidu 官方计费 API。当前没有随项目交付一个能真实向 Vidu 下单的网关。**

只有 Vidu 官网账号并不能获得支付商户密钥、订单 Webhook 或代注册权限。继续完成真实购买，需要 Vidu 或获授权的计费供应方提供套餐、账号对应、创建结账和订单/权益查询能力，再将它们转换成下述格式。不能用开发者自己的 Stripe 收款代替购买用户的 Vidu 官网套餐，也不能用 API 平台积分冒充官网会员。

## 信任关系

智能体只调用映伴 HTTP/MCP。映伴从部署配置取得 `base_url` 和秘密管理中的 `token_env`，以 `Authorization: Bearer <网关凭据>` 访问网关。用户不能在工具参数里指定上游地址、账号引用、支付状态或回调签名。

`account_refs` 将已验证的智能体用户 `sub` 映射到上游 Vidu 账号。这个映射必须来自实际账号绑定，不是由邮箱相似、浏览器当前账号或智能体自述推断。不同用户不能共享账号引用，视频与计费应绑定同一真实账号。

只允许 HTTPS；服务不跟随重定向，响应最多 256 KiB。网关应关闭代理层对结账 POST 的自动重试，并对 `request_id` 实现持久化防重复。密钥轮换通过服务器环境配置完成；完整请求、响应、结账链接不要进入普通访问日志。

## 1. 套餐目录

`GET /v1/catalog?account_ref=<绑定账号引用>`

返回 `account_ref` 和 `plans` 数组；每个计划必须包含以下真实数据。没有可靠套餐数据时返回错误，不能返回默认价格。

| 字段 | 类型 / 语义 |
| --- | --- |
| `plan_id`, `name` | 上游套餐标识和官方显示名称 |
| `currency` | 当前只接受 `USD`，必须显式提供 |
| `billing_cycle` | 当前只接受 `monthly`，必须显式提供 |
| `amount_minor` | 本次授权范围内准确应付金额，整数分，必须大于零 |
| `renewal_amount_minor` | 下次每月续费金额，整数分；非续费商品可为 null |
| `recurring` | 布尔值；为 true 时续费价不得为 null |
| `credits` | 对应官网月度积分，正整数 |
| `source` | 必须为 `vidu_website`，不能是演示或 API 平台额度 |
| `source_text` | 供服务器保留的真实条款来源说明，不回传给智能体 |

目录必须针对请求账号，反映其实际优惠和购买资格。不能省略币种或周期，让服务按默认值猜测。重复套餐 ID、字符串金额、错误账号或来源将被拒绝。

服务对每份报价保存账号引用和三分钟有效期；账号换绑后不允许继续使用旧报价。当前没有交易币种兑换、税费重新报价和自动调价能力：如果实际应付金额或续费条款与报价不一致，应停止本次购买，让用户重新取得并确认新报价。

## 2. 创建官方结账

`POST /v1/checkouts`

请求字段：`account_ref`、`request_id`、`plan_id`、`amount_minor`、`currency`、`billing_cycle`、`renewal_amount_minor`、`recurring`。

`request_id` 是映伴在联网前持久化的购买 UUID。同一次购买永远使用它，上游必须以它查询和去重。网关创建 Vidu 的官方订单/结账会话；不会代替用户确认支付。

成功响应必须原样确认请求中的全部字段，并增加 `checkout_url`、`checkout_reference`。返回 URL 必须属于部署配置 `checkout_hosts` 精确允许的域名；默认只接受 `checkout.stripe.com` 的有效 `cs_live_...` 会话路径。Stripe URL 中的会话编号必须等于 `checkout_reference`。这只是格式和归属校验，**不代表已确认付款**。

网关发现价格、税费、自动续费条款或购买资格发生变化时，不能擅自创建不同条款的订单。返回失败并保留 `request_id` 查询结果。映伴对超时、错误状态或无法核验的成功响应统一保留 `verification_required`，不会自动重发结账 POST。

目前“明确创建失败”与“可能已创建但响应丢失”都会停留待核查，不能自行另起请求制造重复订单。后续若需要更细的取消/失败恢复，需要上游提供确定的终态证据。

## 3. 查询订单与权益

`GET /v1/orders/by-request/{request_id}?account_ref=<绑定账号引用>`

没有对应订单时返回 HTTP 404；它只表示暂未查到，不能作为允许再次下单的证据。其他非成功状态不得伪装成“未付款”。

成功响应包含：

| 字段 | 要求 |
| --- | --- |
| `account_ref`, `request_id` | 与当前账号和原请求严格一致 |
| `plan_id`, `currency`, `amount_minor` | 与原报价一致，金额为严格整数 |
| `order_reference` | 稳定、唯一、非空的官方订单编号 |
| `payment_succeeded` | 严格布尔值，必须来自上游可信付款状态 |
| `entitlement_active` | 严格布尔值，必须确认此订单的官网权益已生效 |

用户口述“已支付”、支付页关闭、回跳 URL、HTTP 200、余额增加，均不能设置上述两个成功状态。网关必须从官方订单查询或验证签名、处理重放的官方 Webhook 得到证据。映伴当前没有向客户端开放 Webhook 或“标记成功”的入口。

`payment_succeeded=true` 且 `entitlement_active=false` 时为 `paid_pending_entitlement`；两者都为 true 才是 `ready`。错误账号、套餐、金额或重复官方订单编号不能完成购买。真实订单已经付款但金额与原授权不同，应停止自动处理并人工核实，不偷偷放宽校验。

## 上游接入验收

取得真实合作接入后验证：同一 `request_id` 永不重复下单；超时能查询原单；套餐、币种、金额及续费条款一致；支付完成但权益延迟时不报告可用；另一账号不能查询或使用订单；回跳和伪造通知不能改变支付结果。

最后在用户明确确认某笔交易后，完成一次真实付款和官网权益核验。届时记录实际订单引用与核验时间，不保存支付卡信息。支付验收通过后依然只通知可以使用，等待用户新的生成确认。
